## Architecture Decisions

- shadcn/ui configured with `base-nova` style, CSS variables, RSC enabled, lucide icon library.
- All theme colors defined as CSS custom properties in `globals.css` (`:root` only — no light mode). Mapped to Tailwind utilities via `@theme inline`. Project tokens (`--bg-base`, `--text-primary`, etc.) coexist with shadcn tokens (`--background`, `--foreground`, etc.) — both set to the same dark values.
- `components/ui/*` files are protected — do not modify after installation.
- Auth runs through `proxy.ts` (Next 16 renamed Middleware → Proxy); `clerkMiddleware` is exported as the proxy default. Public routes are derived from `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL`; everything else is `auth.protect()`-gated.
- Clerk appearance is shared via `lib/clerk-appearance.ts` so server (provider) and client surfaces stay consistent. It uses Clerk's `dark` theme as the base and overrides `variables` with `var(--...)` references — no hardcoded colors.
- Auth pages live under a route group `app/(auth)/...` with a shared two-panel layout; Clerk's default user menu and profile flows are kept intact (mounted via `<UserButton />`).
- Project dialog state is owned by a single hook (`useProjectDialogs`) and shared via `ProjectDialogsProvider`. Dialogs are mounted once in `EditorShell`; consumers only call `openCreate` / `openRename` / `openDelete`. No persistence yet — `submit()` is a no-op placeholder that resolves and closes the dialog.
- Prisma 7 multi-file schema: `prisma.config.ts` points `schema` at the `prisma/` directory, so `prisma/schema.prisma` (generator + datasource) and `prisma/models/*.prisma` are merged at generate time. Generator output is `app/generated/prisma/` (gitignored); client is imported from `@/app/generated/prisma/client`.
- Prisma client adapter selection runs at module load — switching `DATABASE_URL` prefix between `postgres://` and `prisma+postgres://` selects the adapter for the next process start, not at runtime.
- Project API routes return JSON envelopes (`{ project }` / `{ projects }`) and use HTTP semantics for errors: `400` invalid input, `401` unauthenticated, `403` non-owner mutation, `404` project not found, `409` duplicate project id, `204` successful delete. Owner check happens before any write — `404` is returned for missing IDs (existence is not obscured from authenticated users).
- Project ID equals the Liveblocks room ID. Clients compute the room ID as `${slugify(name)}-${6-hex-char-suffix}` and pass it as `id` to `POST /api/projects`; the server validates the format and uses it directly. When `id` is omitted, Prisma falls back to its `cuid()` default.
- Editor data flow: `app/editor/layout.tsx` (server) fetches projects via `lib/projects.ts#getProjectsForUser` and passes them down. The sidebar never fetches projects client-side; mutations rely on `router.refresh()` to re-run the server layout.
- Shared projects are resolved by matching `ProjectCollaborator.email` against Clerk's `currentUser().primaryEmailAddress`. Owned projects are filtered out of the shared list. Users without a primary email see an empty shared list.
- Workspace access checks live in `lib/project-access.ts` (`getCurrentIdentity`, `getProjectAccess`) so the `/editor/[roomId]` server component stays thin. `not-found` and `denied` both render the same `AccessDenied` view — existence of foreign projects is not revealed to the requester. Unauthenticated visits to a workspace `redirect("/sign-in")` (Proxy would also catch this, but the page enforces it explicitly).
- `EditorShell` derives the active project client-side from `usePathname()` against the `owned`/`shared` lists already passed by the server layout. No extra fetch in the workspace page for chrome; if the user lacks access (and the project isn't in their lists), the navbar falls back to no project name and the page itself renders `AccessDenied`.
- Collaborators are persisted by email only (`ProjectCollaborator`, no local user table). Clerk Backend API (`clerkClient().users.getUserList({ emailAddress })`) enriches emails with display name + avatar at read time; it is best-effort — unmatched emails and any Clerk failure degrade to email-only views (the `enrichCollaborators` lookup is wrapped in try/catch). Invite stores `email.trim().toLowerCase()` so it matches Clerk's normalized primary email used by the shared-project access checks.
- Ownership for invite/remove is enforced server-side via `authorizeProjectOwner`; reading the collaborator list is allowed for owners and collaborators via `authorizeProjectViewer`. The share dialog's owner-vs-collaborator UI (`isOwner` from the client `owned` list) is presentation only — the API is the source of truth.
- Collaborator routes reuse the project HTTP-status conventions: `400` invalid email/JSON, `401` unauthenticated, `403` non-owner mutation / non-member read, `404` missing project or collaborator, `409` duplicate collaborator, `201` invite, `204` removal. Removal is keyed by collaborator record id scoped to `projectId` (`deleteMany`), not by email.
- Liveblocks room ID equals the project ID (already equal to the Clerk-facing project id / slug-suffix). Auth uses **access tokens** (`prepareSession` + `session.allow(room, FULL_ACCESS)`), not ID tokens: our PostgreSQL `getProjectAccess` is the single source of truth for membership, so the auth route verifies access per request and grants a session scoped to that one room. Rooms are still pre-created via `getOrCreateRoom` (private `defaultAccesses: []`, `metadata.projectName`) to satisfy the "ensure room exists" invariant and to carry the project name — room-level permissions are intentionally left private since access tokens bypass them.
- Cursor colors are deterministic from the Clerk user ID (`lib/cursor-color.ts`), kept separate from `globals.css` theme tokens so they stay saturated and mutually distinct on the dark canvas. The color is computed server-side at token-issue time and travels in the Liveblocks `UserMeta.info.color`.
- `lib/liveblocks.ts` mirrors `lib/prisma.ts`'s cached-singleton pattern (cached on `globalThis` outside production) so the `@liveblocks/node` client is reused across hot reloads / requests.
- Canvas state is owned by `useLiveblocksFlow` (`@liveblocks/react-flow`), which stores the diagram under its own default `"flow"` Storage key as a typed `LiveObject<{ nodes, edges }>`. `liveblocks.config.ts` still declares no global `Storage` type — the hook manages its own typed subtree — and the app adds no separate canvas persistence here; the room is the live source of truth. Blob snapshot persistence (`Project.canvasJsonPath`) is deferred to a later feature.
- Workspace canvas composition keeps the server/client split: the `/editor/[roomId]` server page enforces membership (`getProjectAccess`) and only then mounts the client `CanvasRoom`, which connects to the room via the existing `/api/liveblocks-auth` access-token flow (room ID == project ID == `roomId` param). No Liveblocks connection runs until access is verified twice — once server-side at render gate, once per-request at token issuance.
- Canvas loading/error handling uses the Liveblocks-recommended suspense pattern: suspense hooks (`@liveblocks/react/suspense`) throw connection/permission errors that a `react-error-boundary` `ErrorBoundary` catches (the "Connection lost" fallback), while `ClientSideSuspense` shows the loading fallback until Storage is ready. Both fallbacks are scoped to the canvas subtree, not the whole app.
- `initialPresence` is `{ cursor: null, isThinking: false }`: the spec calls for `cursor: null`, and `isThinking: false` is included to satisfy the declared `Presence` type (it is not yet read/written anywhere). Live cursor rendering (`<Cursors />`) is intentionally deferred — presence is established, not yet visualized.
- Node creation goes through React Flow's change pipeline: a dropped shape becomes a `{ type: "add", item: node }` `NodeChange` passed to the `onNodesChange` returned by `useLiveblocksFlow`, which persists the add to the shared Storage `LiveMap` of nodes. The app never mutates Storage directly for canvas content — `useLiveblocksFlow` remains the single owner, so adds sync to collaborators automatically.
- The drag/drop contract is isolated in `lib/shape-drag.ts` behind a namespaced custom MIME (`application/x-ghost-shape`) and a validating parser, keeping the components free of serialization logic and treating drop data as untrusted boundary input (per `code-standards.md`). Default per-shape sizes live in `types/canvas.ts` (`NODE_SHAPE_DEFAULT_SIZES`) so both the drag source and any future drop logic share one source of truth.
- New nodes get an explicit pixel size via the React Flow node `style: { width, height }` (not `data`), so an empty-label node is still a visible, grabbable box of its default size. The basic `canvasNode` renderer fills that box (`h-full w-full`) and reads only `data.color` for the fill; shape geometry, connection handles, and the per-shape text color from `NODE_COLORS` are deferred to the shape-visuals feature.
- `CanvasFlow` is split into an outer `ReactFlowProvider` shell and an inner `CanvasFlowInner` so `useReactFlow().screenToFlowPosition` (which requires the provider context) is available in the same component that owns the drop handler. Node IDs combine shape + `Date.now()` + a `useRef` counter to stay unique even for multiple drops within the same millisecond.
